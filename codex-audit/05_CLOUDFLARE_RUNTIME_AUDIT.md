### Critical observation: production `USE_MOCK_AI = "false"` does not switch the model router to real AI

`services/model-router.ts:33-39`:

```ts
const provider: ModelResponse["provider"] = this.env.USE_MOCK_AI === "true" ? "mock" : "workers_ai";
const model = this.selectModel(request.category);
const text = provider === "mock"
  ? `Mock ${request.category} output for: ${request.prompt.slice(0, 120)}`
  : `Configured ${provider} call placeholder for ${model}.`;
```

In production, the router returns the literal string `"Configured workers_ai call placeholder for kimi-2.6."`. The `env.AI` binding is never used. **Production AI is silently mocked.**

### Cloudflare environment-binding inheritance

Cloudflare Wrangler does **not** inherit top-level bindings into named environments — env-specific bindings must be declared explicitly. Codex got this right: every binding is duplicated in `env.staging` and `env.production` blocks. The shape matches the top-level. ✅

### Worker entrypoint exports

`src/server/index.ts:25-35` exports MarketingAgent, MustBeViralMCP, all 7 Workflow classes. ✅ Required for Workers DO/Workflow bindings to find their implementing classes.

> Action required: Migrate from @cloudflare/workers-types to generated runtime types. `wrangler types` now generates runtime types and supersedes `@cloudflare/workers-types`. You should now uninstall `@cloudflare/workers-types` and remove it from your tsconfig.json.

Codex has not actioned this. Low severity.

## Compatibility date / runtime mismatch

BUILD_LOG Milestone 6 notes the local Workers runtime supports compat date `2025-11-25`, so dev logs warn about falling back from `2026-05-08`. Production deploy applies the configured date as-is. Acceptable but worth noting.

## Rules-of-Workflows compliance

Cloudflare's Workflow rules require that `step.do(...)` callbacks be deterministic and safe to retry. Stub `runWorkflowStub` does a single `step.do("…:stub", () => Promise.resolve(...))`, which is trivially deterministic. ✅ No violation, but no real workflow logic either.

## Rules-of-Durable-Objects compliance

`MarketingAgent.fetch` reads/writes `ctx.storage` synchronously per request and returns immediately. No `setInterval` / `alarms` / `setTimeout`. ✅ No violation.

`MarketingAgent.updateState` does the canonical read-modify-write under `ctx.storage`, which serialises requests to the DO instance. ✅
